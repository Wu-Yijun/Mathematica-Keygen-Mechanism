# 05 — Accepted CRC 表

**中文** · [English](05-accepted-crc.md)

## 5.1 Accepted CRC 究竟是什么

条件 B 所要求的值在早期的文章中被称为**魔数**（在公开的参考实现中则称为
*初始哈希*）。反编译出的代码揭示了它的真实身份：**条件 B 的输出**，它必须是
一个**内置表**（白名单）的成员。

```
  acceptedCrc = CRC16(poly = 0x105c3, init = 0xa5b6, n0 ‖ MESSAGE)
```

**每个构建一张表**。它是该方案中最接近密钥的东西。

## 5.2 提取原理（是什么让它们能在二进制中被找到）

白名单以一个普通的、由小端序 `u32` 组成的数组存储，其中每个元素都是一个有效的
16 位值，其后紧跟着元素计数：

```
  .data:  [ m_0 ][ m_1 ] … [ m_{K-1} ][ K ]        (each cell 4 bytes)
```

校验器*使用*它的方式是一个成员判定循环：

```
  lea  rcx, [rip + <table>]      ; &m_0
  ...                            ; 某个构建可能读取 <count>，也可能把 K 折成常数
  cmp  [rcx], eax                ; table[i] == acceptedCrc ?
  je   accepted
```

因此可靠的提取方式是**以代码定位、以形状校验**：

1. **定位校验器。** 找到许可相关字符串（`Bad password.`、
   `Password not in format dddd-ddd-ddd.`）、引用它们的代码（RIP 相对的
   `lea`/`mov`），并用 `.pdata` 得到所在函数的边界。
2. **收集它的数据操作数。** 这些函数内所有指向 `.data`/`.rdata` 的 RIP 相对操作数。
3. **校验形状。** 若自某地址起的 `K` 个字都落在 `1..0xffff` 且紧随其后的那个字等于
   `K`，它就是一个表首。两个方向都要试：构建既可能引用表，也可能只引用长度。

纯**结构扫描**（一串小 `u32`，其下一个字或最后一个元素等于串长）现在只作兜底，
单独使用并不可靠：

- 计数可能被折成代码里的常数，数据里就没有任何东西把它与数组关联起来——而朴素规则
  依赖这种相邻性；
- 更糟的是，“小值串”可能**越过计数**继续延伸到下一个数组，于是串长不再等于 `K`，
  “下一个字 == 串长”的判据随即失效。

**例（14.2）。** 14.2 的内核（`WolframEngine.dll`，SHA-256
`cb58c2541b8f40abb0292859d5004a77a61d300f2f1efdb17c5a5feed530765d`）恰好两种情况同时
发生：计数之后的数据是另一个 16 位值数组，于是结构扫描什么也找不到；而代码定位扫描
找到了表——**`0x18681adf0`**（计数 `21`，被 `0x181c3587b` 引用）。15.0.1 属于运气好的
情形：其计数之后的字 `> 0xffff`，朴素扫描正好能命中：

| 项目 | 15.0.1 | 14.2 |
| --- | --- | --- |
| table VA | `0x186d4dd40` | `0x18681adf0` |
| count | `21`（存于 `0x186d4dd94`） | `21`（存于 `0x18681ae44`，并被折成循环常数） |
| referenced from | `0x181cf3650`（CRC 校验器） | `0x181c35160`（CRC 校验器） |

```
14.2 :  61182  31889  22384  31827  25836  29678  16905  35954  44011  33360  35944
        59222  46288  52525   8925  26304  54607  45075  21527  53711  24735
```

**一个构建里可能有两张成员判定表。** 14.2 的校验器把 CRC 分别与**两个**数组比较：
`0x18681adf0`（21 项）与 `0x18681ae48`（10 项），两处都是逐元素比较
（`lea rax,[rip+…]` 之后紧跟 `cmp [rax], ebx`）。二者取值互不相交。仅凭这些字节还无法
断定哪张表服务于哪种密码，但它们的稳定性很说明问题：

| 二进制 | 10 项表 | 21 项表 |
| --- | --- | --- |
| 14.2 `WolframEngine.dll` | 有 | 14.2 自己的 |
| 15.0.1 `WolframEngine.dll` | **没有** | 15.0.1 自己的 |
| 15.0.1 `SessionManager.exe` | 与 14.2 的逐字节相同 | 与 15.0.1 内核的相同 |
| 15.0.1 `WSMKernelX.exe` | 与 14.2 的逐字节相同 | 与 15.0.1 内核的相同 |

**10 项表是许可代码里的“冻结常量”**（14.2 内核与两个 15.0.1 组件里完全相同），而
**21 项表随构建重新生成**（15.0.1 的内核、SessionManager、WSMKernelX 三者一致，但与 14.2
不同）。一个自然但尚未证实的解读是：10 项表属于更早（≤ 14.0）的密码格式——那套方案已经
不再变化——而 15.0.1 的**内核**干脆不再带上这条代码路径。要落实它，可以：把更多版本的
`WolframEngine.dll` 喂给 `extractAcceptedCrcTables()`，统计每个二进制里有几张成员判定表；
或者运行时构造一个旧格式密码，看内核是否接受。

两张 21 项表接近但**不是旋转**：21 个值里 18 个相同，但相同的值是按**块重排**的
（15.0.1 读作 `A B C`；14.2 读作 `61182 B 44011 33360 A C`，其中 A = 9 个值、B = 7 个、
C = 2 个），且各自都有三个对方没有的值（14.2 多 `61182`、`44011`、`33360`；15.0.1 多
`28536`、`11836`、`61068`）。`main@v14.1.0.js` 里那份 v14.1 时代的公开列表与 14.2 有四个
值重合（`33360`、`44011`、`35944`、`59222`），与 15.0.1 只有两个——而它的默认值 `24816`
在两者中都不存在。两个内核的样本远不足以归纳出规律；目前数据能说明的是：这张表是**通过
编辑演化**的（值会增删，且多与相邻版本共享），而不是每个构建独立随机生成。

两种方法都在 [code/accepted-crc-table.ts](code/accepted-crc-table.ts) 中实现
（`extractAcceptedCrcTables()` = 先代码定位，再以结构扫描兜底）；二者都不需要反汇编器。

## 5.3 按提取结果列出的 v15.0.1 白名单

`WolframEngine.dll`（SHA-256 `9a9a7d88…`）：

| 项目 | 值 |
| --- | --- |
| table VA | `0x186d4dd40`（文件偏移 `0x6d4cb40`，`.data`） |
| count VA | `0x186d4dd94` = **21** |
| referenced from | `0x181cf3650`（CRC 校验器），位于 `0x181cf3d0e`（`lea rcx,[rip+0x505a02b]`） |

```
35944  59222  46288  52525   8925  26304  54607  45075  21527  31889  22384
31827  25836  29678  16905  35954  53711  24735  28536  11836  61068
```

交叉核对：

- **相同的结构规则**在 `SessionManager.exe` 中找到了相同的表
  （`DAT_140659e20`，计数 `DAT_140659e74 = 21`），仅有一个条目不同：
  那里是 `16897`，而 `WolframEngine.dll` 中是 `16905`——这证明白名单是
  **因模块/构建而异的**。
- 对 `WolframEngine.dll` 的全文件结构扫描找到了**恰好一个**这种形状的表
  （其他匹配是五个不相关的 5 元素整数数组）。因此，该构建的 Accepted CRC 集合
  已被完全枚举。
- `SessionManager.exe` 另外还有一个**第二**表，仅当某个模式标志
  等于 `"Y"` 时使用（`DAT_140659e78`，10 个条目）；`WolframEngine.dll` v15.0.1 不包含
  它，即该模式在那里未被使用。

## 5.4 设计理由——为什么是一张由这些数字组成的表？

条件 B 本可以使用单个常量，但那样每个产品都将共享一个
密钥。使用一个*集合*可以让同一个二进制验证**多个版本/产品**，由服务端
选择与产品匹配的那个条目。该集合小到可以廉价地嵌入，又
大到使盲目猜测可以忽略不计（`21 / 2¹⁶ ≈ 0.03 %`）。

## 5.5 这些值是否遵循某种模式？（分析）

针对这 21 个值计算出的统计量：

| 属性 | 结果 |
| --- | --- |
| 范围 | `8925 … 61068`，全部 `< 2¹⁶` |
| 均值 | `34513`（≈ `2¹⁶ / 1.90`） |
| 奇偶性 | 10 奇 / 11 偶（平衡） |
| 质数 | **0**（全部为合数） |
| 排序后的间隔 | `2911, 5069, 4622, 857, 2351, 1101, 468, 2232, 1142, 2149, 62, 4055, 10, 9121, 1213, 6237, 1186, 896, 4615, 1846`——不规则 |
| 等差数列？ | 否 |
| `CRC_B(0xa5b6, "<product name>")` 针对 `Mathematica`、`Player`、`Wolfram`、`Wolfram One`、`Finance Platform`、…… | 无一落入表中 |

结论（对确定性保持明确）：

- **已观察到：** 这些值是不透明的、分布良好的 16 位常量，从单个构建中
  无法检测出任何算术结构。它们表现得像是*被指派*的产品/版本
  标识符（或者是某个未知的每版本种子的 CRC 输出）。
- **尚未确立：** 每个值是产品名称的 CRC、产品代码的 CRC，
  还是随机指派的。要判定这一点需要服务端或多个正版许可证。
- “0 个质数”的观察很可能是巧合（21 个随机 16 位值
  `P(all-composite) ≈ 0.14`），并且**不**被用作某条规则的证据。

## 5.6 对*这个*构建而言哪个值才是正确的

重要的是这张表，而非任何外部列表。经验上：

- 正版许可证的 Accepted CRC 是 `59222`——它**在**此构建的表中，
  用它重新生成即可复现正版密码。
- 公开概念验证中的值 `24816` **不**在此构建的表中，
  会被拒绝。（该公开列表中只有 `59222` 和 `35944` 与此处的
  21 个条目重合。）

因此，“Accepted CRC”是因构建而异的；稳健的做法是用
[code/accepted-crc-table.ts](code/accepted-crc-table.ts) **从确切的二进制中提取该表**，并使用其中
的某个条目。
